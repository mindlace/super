superpowers-reader

A plugin that shows a spec or plan beside the chat as soon as it is written, styled by superspec's stylesheet, with nothing to install but Node.

Intent

When Claude writes a spec or a plan as HTML, the person has to go and find it: start superspec, pick the document from a list, and keep that tab beside the chat. The document they want is always the one that was just written.

This plugin puts that document in the desktop app's browser pane the moment it is written. It looks as it does in superspec, follows light and dark mode, and refreshes itself while Claude keeps editing.

The plugin carries a small static file server and nothing else. Installing it runs no build and fetches no packages.

Goals, non-goals, anti-goals

Goals

  • A new plugin, superpowers-reader, in this marketplace.
  • Install is free if Node is on the path: no npm install, no build step, no bundled dependencies.
  • After a Write or Edit of a spec-format .html file anywhere under a docs/ directory, the document is shown in the browser pane. docs/superpowers/specs and docs/superpowers/plans are the usual places, not the only ones.
  • The page is painted by spec.css, the same file superspec uses, and follows the app's light or dark theme.
  • The page refreshes itself when the file changes and keeps the scroll position.
  • Images and video beside the document load, under the format's Media rules.
  • Code blocks are coloured by their data-lang, by a highlighter file the plugin carries.
  • In the Claude Code CLI, where there is no browser pane, each newly written document gets a line in the transcript with a link to it on the reader server.
  • A document's address reads as its path: http://localhost:4520/s/Users/me/proj/docs/superpowers/specs/foo-design.html.
  • The plugin fails open. If anything it needs is missing, the write still succeeds and the session carries on.

Non-goals

  • A document list, search, tabs or spec-and-plan pairing. Superspec keeps those.
  • Markdown specs and plans. Only .html documents are shown.
  • Reporting structure problems (missing ids, duplicate ids). Superspec keeps that.
  • Heading anchor marks and the path bar.
  • Surfaces other than the desktop app and the CLI.
  • Opening the person's own browser for them from the CLI. The link is theirs to click.
  • Windows paths.

Anti-goals

  • An install step of any kind.
  • A server that outlives the session that started it.
  • Serving any file that is not under a docs/ directory.
  • Wrapping an HTML file that is a whole page of its own, such as generated API documentation.
  • Running script that a document carries.
  • Changing a spec file, the spec format, or what superpowers-html writes.
  • Needing superspec to be running, or superpowers-html to be installed.

Constraints

These were found by trying things in the session that produced this spec.

  • A plugin's own pane cannot draw HTML or CSS. It draws from a fixed set of elements with the app's typography. A spike that translated the format into those elements kept the structure and lost the layout.
  • The app shows a local .html file as a static snapshot that is always told the theme is light. A page served from http://127.0.0.1 or http://localhost in the same pane is told the real theme.
  • A plugin can run code on tool calls through a hooks module. That module has no Node and no DOM. It reaches files, HTTP, tools and child processes through the engine.
  • A hooks module can send the browser pane to an address by calling the pane's navigate tool after a Write. A spike did exactly that when this file was first written.
  • A child process a hooks module starts is killed when the module unloads or the session ends.
  • The hooks module API is marked early access and may change between releases.
  • When a plugin is installed from this marketplace, a symlink inside it becomes a regular file. superpowers-html already relies on this for spec-format.md.
  • spec.css is self-contained: no imports, no web fonts, and everything is scoped under .spec-doc.
  • tests/test_manifests.sh holds the exact list of marketplace plugins.

The reader server

node reader/server.mjs
# first line on stdout, then it serves until it is killed:
{"port": 4520}
  • It listens on 127.0.0.1. It asks for port 4520 first. If that port is taken, it takes one the operating system picks.
  • Links name the host as localhost.
  • It imports only node: modules.
  • It answers GET and HEAD. Any other method is a 405.
  • A request whose Host name is not 127.0.0.1 or localhost is a 403.
  • It exits on SIGTERM, SIGINT and SIGHUP, and when its parent process goes away, so it cannot outlive the session. It does not read standard input: the engine closes a child's standard input from the start.
  • It keeps no state and writes nothing to disk.
Routes
RequestAnswer
/s/<file path>.htmlThe page for that document. See The page.
/s/<file path>.html?fragment=1The file's bytes, with an ETag.
/s/<dir>/assets/<file>A media file, with Range support.
/_/spec.cssThe stylesheet.
/_/page.css, /_/page.jsThe page's own files.
/_/highlight.min.jsThe vendored highlighter.
Anything else404.

The part of the address after /s is the file's absolute path. A relative src in a document therefore resolves to the right file with no rewriting.

Decision (builder's call) Port 4520 is preferred so that a link usually stays the same from one session to the next. Superspec keeps 4510. Each session still runs its own server, so a second session at the same time gets another port.

Which files are served

document  <any>/docs/<zero or more segments>/<name>.html
media     <any>/docs/<zero or more segments>/<name>.<ext>
ext       png jpg jpeg gif webp mp4 webm
  • The path must have a segment named exactly docs. Everything below it is in reach; nothing else is.
  • A document must be in the spec format: its first element is article, after any white space or comments. An .html file that starts with a doctype, html or anything else is a 404. It is a page of its own and the reader does not wrap it.
  • The path is decoded and normalised before it is checked. A path that still holds .. is a 404.
  • The file's real path, after symlinks are resolved, must match the same shape. Otherwise the answer is 404.
  • The file must be a regular file.
  • Every answer carries X-Content-Type-Options: nosniff, Cache-Control: no-store and Cross-Origin-Resource-Policy: same-origin, so another website cannot embed a document or probe for files.
  • The page carries its content's ETag on main as data-etag, and the script starts from it, so the first refresh check already knows what the page shows.
  • The path is not limited to one projects folder. The shape is the guard.

The page

The server wraps the file's content, unchanged, in a small document.

<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>(the document's h1, or its file name)</title>
    <link rel="stylesheet" href="/_/spec.css">
    <link rel="stylesheet" href="/_/page.css">
    <script src="/_/highlight.min.js" defer></script>
    <script src="/_/page.js" defer></script>
  </head>
  <body class="spec-doc">
    <main>(the file's content)</main>
  </body>
</html>

The page answer carries this header.

Content-Security-Policy: default-src 'none'; style-src 'self'; script-src 'self';
  img-src 'self'; media-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'none'
Decision (builder's call) The page is made safe by that policy, not by a sanitizer. A sanitizer needs a package. Under the policy a script, an event handler or a style attribute in a document does nothing, and a remote src does not load.

The script does five things.

  • It colours every pre > code block that has a data-lang the highlighter knows. A block with an unknown language, or with none, is left plain.
  • It disables every checkbox, so the page never looks editable.
  • It gives every http and https link target="_blank" and rel="noopener", so a click does not replace the document.
  • Every two seconds, while the page is visible, it asks for ?fragment=1 with If-None-Match. On a changed answer it replaces the content of main, repeats the three steps above, and leaves the scroll position alone.
  • If that request answers 404, it shows one line above the document saying the file is gone, and keeps the last content.
Decision The owner chose to vendor a highlighter. The builder's call is highlight.js: it is one prebuilt file, it marks tokens with classes, so it works under the policy above, and its GitHub light and dark colours are close to the ones superspec shows. Its colours go in page.css, light by default and dark under prefers-color-scheme.

Two known differences from superspec. Markup outside the format is not removed: it is left inert and shown as the browser shows it. Code colours come from a different highlighter, so some tokens differ.

The hooks module

  • It listens to Write and Edit tool calls and lets each run first. It never changes a call or its result.
  • When the written file is a document under the rules in Which files are served, it shows that document. That includes the check that the file starts with article, so writing some other HTML file under docs/ does nothing.
  • To show a document it first makes sure the server is running. What it does next depends on where the session runs.
  • In the desktop app it opens the document's address in the reader's own browser-pane tab.
  • In the CLI it writes one line to the transcript, naming the document and giving its address as a link. It does this once per document, not on every edit.
  • The reader's tab is one the module opened itself. It opens that tab the first time, reuses it afterwards, and opens a new one if the person closed it. It never navigates a tab it did not open, so a dev-server preview in the pane is left alone.
  • It brings the reader's tab to the front when it shows a different document, and not otherwise. At the same moment it asks the app to show the Browser pane, in case the person had it hidden. A refusal is ignored.
  • It starts the server at most once per session, on the first document, and reads the port from the first line the server prints.
  • It navigates only when the document differs from the one it last showed. The page refreshes itself, so navigating again would only lose the scroll position.
  • It registers a command, /reader [path], that shows the given document. With no path it shows the document with the latest modification time under any docs/ directory in the session's working directory. In the desktop app the command always navigates. In the CLI it answers with the link.
  • A notice is a short message shown to the person in the app. It is never text added to what Claude reads.
Decision The owner chose any HTML under docs/ over the two superpowers folders. The builder's call is the article check, which keeps the reader to spec-format documents now that the folder no longer says so.
Decision (builder's call) The reader keeps to its own tab. Taking over whatever the pane is showing on every spec write would be the behaviour most likely to annoy.

Changes outside the plugin

  • .claude-plugin/marketplace.json gains the plugin.
  • README.md lists four plugins, adds the install line, and says how the reader relates to superspec.
  • tests/test_manifests.sh expects the new plugin name.
  • tests/test_format_links.sh checks the spec.css symlink as it checks the others.
  • tests/run.sh runs the reader's tests.

Superspec itself is not changed.

Proved live

The design rests on three things a hooks module must be able to do. All three were seen working in a desktop app session on 2026-11-20, using the spike.

  • It sent the browser pane to an address after a Write.
  • It started a Node child process and read the first line the child printed. The child was gone once the module stopped reading.
  • Its Write hook fired for a document a subagent wrote, with the subagent's id on the call.

Not yet seen: what happens to the child when the whole session ends abruptly. The server's watch on its parent process covers that case.

The spike and the test tools

A working spike of the hooks module exists outside the repository. It is the starting point for hooks/register.ts, not code to keep as it is: it opens superspec on a fixed port and navigates the active tab.

  hooks/hooks.json      { "modules": ["./register.ts"] }
  hooks/register.ts     the module
  tests/open.test.ts    its tests
  .claude-plugin/types/ the API's type declarations, written by the app
  • A hooks module's tests are tests/*.test.ts files that import from claude-code/testing. In a test, a hook stands in for the engine, so a tool call or an HTTP request is answered by the test.
  • claude plugin test <plugin folder> runs them. No Node test runner or fake engine is needed.
  • claude plugin validate <plugin folder> reads the module as the engine will and reports what it would refuse.
  • tests/run.sh runs both only when claude is on the path, as tests/test_manifests.sh already does for validation.
  • The plugin-authoring skill in Claude Code documents the module API and has worked examples.

What done looks like

  • Writing a spec in a session with the plugin installed opens it in the browser pane with no other action.
  • The two reference documents look the same in the reader as in superspec, apart from small differences in code colours, and heading anchors: 2026-11-13-html-spec-writers-design.html here, and a long plan with tables and callouts.
  • Switching the app between light and dark changes the page, code colours included.
  • In a CLI session, writing a spec puts one line with a working link in the transcript, and editing the same spec adds no more lines.
  • With port 4520 taken, the server starts on another port and the link names that port.
  • Editing the file changes the page within a few seconds, and the scroll position holds.
  • A request for a file outside the allowed shape, through .., a symlink or a wrong Host, is refused. Each case has a test.
  • A spec-format file at docs/notes/foo.html is shown. A whole-page HTML file beside it is neither shown nor served.
  • A document holding a script element and an onclick attribute runs neither.
  • The server's tests run with node --test and need no packages.
  • The hooks module passes claude plugin validate and has tests for each row of the outcomes table.
  • sh tests/run.sh passes.

Left to the builder

  • The lowest Node version to support, stated in the README. Nothing in the repository pins one.
  • The rules in page.css. Superspec's page also gets Tailwind's reset, which the reader does not have, so the reference documents decide what is needed.
  • Whether the server's tests live under tests/ at the root or inside the plugin.
  • The wording of the notices and of the CLI's transcript line.
  • The highlight.js version, pinned and recorded beside the file, and which of its published builds to vendor. The common-languages build is enough if it covers ts, js, json, sh, sql, html, css and py. A language it lacks, such as svelte, is shown plain.
  • How the module tells the desktop app from the CLI.
  • How the refresh keeps the scroll position when content above the viewport changes height.
