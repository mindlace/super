Supersonic run records live outside the repo

Move the composer's and conductor's working records from the project's main checkout to ~/.supersonic/, and commit only the design, the specs and the build graph.

Why

Today both skills keep their working records in <project>/.superpowers/superconductor/<design-slug>/, and <project> resolves to the main checkout. That directory is not ignored. The result in sfhousing:

  • The owner keeps main synced with origin/main and never edits it, yet the main checkout filled with about 37 untracked files: checkpoints, prompts, assignments, questions, rulings and helper scripts.
  • The composer committed ledger.md and its surveys on the package branch. The conductor kept writing its own copy in the main checkout. When the feature merged, git pull refused to overwrite the local ledger.
  • Earlier runs committed hundreds of these records to the repo (248 prompts for one design).

The owner wants the records kept for process analysis and forensics, but not in the source repo: outside version control except the design, the specs and the build graph, and not dependent on the state of any clone.

Goals and non-goals

  • Goal. The only files supersonic commits to a project are the design doc, the specs and the build graph. Operators still commit their implementation plans, as now.
  • Goal. Every other record the composer, the conductor, their forks and operators write goes to one local directory per design. It survives crashes, a closed laptop, git clean -fdx and deleting the clone.
  • Goal. Someone who installs supersonic can write there without permission prompts. The skills set this up, with the user approving.
  • Non-goal. Changing the handoff. The composer still ends with the package committed on superconductor/<design-slug>, and the conductor still adopts that branch as its integration branch.
  • Non-goal. Versioning the records. No local git repo in the records directory: ledger.md is already an append-only log, and concurrent writers would contend for git's index lock.
  • Non-goal. Cleaning up records already committed in existing projects such as sfhousing. That is a separate change in each project.
  • Non-goal. superpowers-jev's .superpowers/jev/ log and superpowers' own .superpowers/sdd/ workspaces. Both are out of scope; SDD's workspace is already git-ignored by its own script.
  • Anti-goal. Anything under ~/.claude/. Claude Code treats every .claude path as protected: non-Markdown writes prompt in acceptEdits and no allow rule pre-approves them, so a background operator would stall. This rules out both the per-project folder and ${CLAUDE_PLUGIN_DATA}.

Design

The records directory

The records directory for a design is <home>/superconductor/<repo-key>/<design-slug>/, where:

  • <home> is $SUPERSONIC_HOME when set, else ~/.supersonic. The variable exists for tests.
  • <repo-key> is the absolute path of the repository's main checkout, from git rev-parse --path-format=absolute --git-common-dir with its trailing /.git removed, with every non-alphanumeric character replaced by -. This is the same encoding Claude Code uses for its project folders, so /Users/a/Projects/sfhousing becomes -Users-a-Projects-sfhousing. Every worktree of one repository, including nested package worktrees, maps to the same key.

One small script, shipped with the plugin, prints this path for a given design slug and creates it. Both skills call it once and record the absolute path. Everything downstream (the ledger, beat.sh <dir>, each assignment's Ledger: line, --add-dir) already takes the path as a value, so it carries the new location without further logic.

The directory's contents and layout are unchanged: ledger.md, assignments/, prompts/, questions/, rulings/, checkpoint-*.json, surveys/, timer, and so on.

What the composer commits

Phase C5's commit lists exactly the design doc, the specs and the build graph. Survey reports, fresh-eyes reports, amendments, briefs, helper scripts the composer writes for itself, and the ledger go in the records directory and are never committed. The skill says so where it today says "survey reports worth keeping" and "ledger records", and its forks follow the same rule.

The conductor and operators

  • Every place that names <project>/.superpowers/superconductor/<design-slug>/ names the records directory instead: superconductor Phase 0 and the ledger format, supercomposer's ledger rule, composer-forks.md, operator-briefing.md where it applies, and beat.sh's usage comment.
  • The conductor never copies records into a branch, and never commits them.
  • Old runs. On resume, when the records directory has no ledger but <main checkout>/.superpowers/superconductor/<design-slug>/ledger.md exists, the conductor copies that whole directory into the records directory and deletes the copied files that git does not track. Tracked files stay for the project's own cleanup. It records one ledger line saying so.

Setup for anyone who installs supersonic

A plugin cannot change user permissions by itself, so the skills check and offer:

  • At the start of supercomposer (C0) and superconductor (Phase 0), the skill checks whether ~/.supersonic (or $SUPERSONIC_HOME) is covered by permissions.additionalDirectories in the user's settings, or by the session's own --add-dir.
  • If it is not, the skill tells the user once why it is needed and asks to add it to the user settings file (~/.claude/settings.json, or under $CLAUDE_CONFIG_DIR). The user approves that one edit. If they decline, the skill continues and the user answers write prompts as they come; the skill says this.
  • The README's install section states the requirement and shows the settings line, so a reader can add it before the first run.
{ "permissions": { "additionalDirectories": ["~/.supersonic"] } }

Left to the builder

  • The script's name and where it lives. It must be reachable from both skills (for example in superconductor/, with supercomposer naming its path).
  • How the setup check reads the settings files: user settings, and $CLAUDE_CONFIG_DIR when set.
  • Updating tests: tests/test_beat_sh.sh, the scenario fixtures under tests/scenarios/ that name the old path, and new tests for the path script (key encoding, worktrees sharing one key, $SUPERSONIC_HOME).
  • The plugin version bump (0.6.0 to 0.7.0) and the README.
